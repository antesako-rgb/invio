## Proposed contract and ownership

The existing public `project_photos` schema stays unchanged. Private tables:

| Table | Responsibility |
| --- | --- |
| `storage_objects` | Server-created reservation, canonical key, state, finalization result; survives project/product deletion. |
| `storage_cleanup_jobs` | Durable DELETE task with lease, attempts, retry time; references only the private ledger. |
| `storage_legacy_review` | Untrusted legacy metadata archived before a photo/project cascade removes its public row. Never authorizes deletion. |

All three have restrictive deny-all RLS. PUBLIC/anon/authenticated/service_role
have no direct table privileges. Only the narrow service-role EXECUTE RPCs expose
the necessary contract; their postgres owner accesses the private schema.
No new default privileges, unrelated grants, or existing policy changes.

`storage_reserve_upload` resolves the product/project in the DB and returns
`{ id, storage_key, expires_at }`. For invitation/album the application obtains
the actor from `auth.getUser()` (not browser input), and the DB checks membership.
For Photo Wall it resolves public ID and checks public/published state. The ID is
generated by server `randomUUID()`, and SQL constructs the only permitted key:

`projects/{resolvedProjectId}/photos/{reservationId}.webp`

The service-role RPCs must NEVER be exposed as generic browser-callable wrappers
accepting actor IDs or arbitrary paths. Existing authenticated arbitrary-path
create RPC grants are revoked in 002. The photo insert trigger rejects objects
without a matching server ledger identity even for a server-side direct insert.

Application `database.types.ts` is intentionally NOT regenerated/falsified:
the proposed RPCs do not exist in the live database yet. The isolated
`storageLifecycleRepository.ts` declares the pending contract, narrows the admin
RPC interface at one explicit boundary, and runtime-parses every data result.
After applying SQL, regenerate the real public types and replace that temporary
interface with the generated function contracts (retain runtime parsing).

## Pending uploads, retry and finalization

1. Validate runtime target/file, obtain verified user for member uploads.
2. Reserve before image optimization or Bunny PUT. A reservation retry uses the
   SAME UUID and checks identical target/actor, so a possible reserve commit does
   not create another object.
3. Optimize, check reservation expiry before starting PUT; PUT has a 120s timeout.
4. Finalize using the same ID. SQL repeats current permission/public-state checks,
   and registers `project_photos` + product association in one transaction.
5. A successful transaction stores its return JSON in the ledger. Repeating the
   finalize RPC while ready returns that result and does not insert duplicates.
6. A finalization timeout is retried once with the same ID. If both calls fail,
   return the existing upload failure state. NEVER delete the object speculatively.

A new user retry creates a new reservation. This package guarantees idempotency
within the server upload operation, not deduplication of separate user uploads.
There is no browser storage/cookie upload identity.

Pending reservations expire after 24h. The sweep waits another hour before
marking them for deletion. Failed optimization/PUT needs no blind compensation;
the private reservation is enough to eventually delete that exact key, including
an object whose PUT response was lost. PUTs do not start within 120s of expiry.
HTTP cancellation does not prove immediate remote cancellation: validate the
hosting/Bunny request-duration bound and grace interval before production cleanup. See [review/REMOTE_PUT.md](REMOTE_PUT.md); the 25h interval is not a provider guarantee.
Never reuse a key, including deleted/timed-out reservations.

## Cleanup and references

All lifecycle operations/association guards use one nonblocking transaction advisory gate.
This is deliberately conservative initial synchronization, not a distributed
framework. Parent document/association guards lock the parent row; conflicting
parent-first operations fail with retryable 40001 if the gate is busy, rather than waiting while holding parent rows. This change still requires real PostgreSQL verification.
Reserve/finalize retry once. Other CRUD retains normal failure handling.

The decision to queue an object checks:

- every `project_photos` row whose Bunny key is identical after the old adapter's
  leading/trailing slash normalization, regardless of project or photo ID;
- all invitation, album, and wall association references for those IDs;
- invitation/album document references, including `unplacedPhotos`;
- legacy archive aliases, including records from deleted projects.

References are checked first using ledger IDs even when the public row is gone.
An exact alias on an unreferenced object requires individual quarantine. Encoded,
dot-segment, URL-shaped or otherwise ambiguous legacy paths block automatic
cleanup globally WITHOUT changing ready states or preventing valid links.
This intentionally trades storage cost for safety until an operator reviews them.
Ownership is attested only by a NEW reservation + server upload + finalization.
No migration bulk-adopts, deletes, relocates or rewrites old objects.

When safe, the transaction changes the object to `deleting`, records a job, and
removes its unreferenced public picker row. Association triggers refuse new links
to a non-ready object. New photo rows cannot create another alias. Both guards
use the same gate as the decision, so adding a link cannot slip between checking
references and marking deletion.

Unlink triggers queue during the RPC transaction, including direct authorized
RPC calls. The project AFTER DELETE hook and regular sweep cover cascades; the
private ledger/jobs have no project FK and remain after a project disappears.
Pending uploads keep their expiry/grace during project deletion.

Workers claim bounded jobs, receive a random lease token (1h lease), and DELETE
only parsed canonical keys. Failure retries after 15min. A crash after DELETE or
before acknowledgement leaves a durable task; retry DELETE/404 is idempotent.
Completion requires the current lease token. Tombstones remain; no key reuse.
There is no routine recursive Bunny directory deletion.

Malformed legacy documents may make reference parsing fail. Cleanup fails closed;
this package does not repair documents as part of storage remediation.

## Rollback

- Before activation and before ANY ledger rows: `rollback_prepare_only.sql` checks
  tables are empty and guards are absent, then removes only the additive package.
- After activation or any reservation: disable scheduler, enter maintenance, use
  `rollback_freeze.sql`. Keep the ledger, legacy archive, jobs and safety triggers.
  Do not deploy old write handlers into open traffic; old upload code PUTs before
  the now-revoked RPC and can recreate the previous failure pattern.
- Continue serving read-only experiences or deploy a maintenance build. Resume
  writes via a reviewed forward fix and explicit service-role re-grants.
- SQL rollback cannot restore an object already deleted from Bunny. Restoration
  requires an independent backup. Replication is not that backup.
