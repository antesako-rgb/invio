# Generic Public RSVP implementation

Public route remains `/invitation/[publicId]`. The existing get_public_invitation parser now validates and retains enabled, max guests >= 1 and nullable capacity >= 1. No direct invitation read was introduced.

InvitationRenderer has an optional ReactNode RSVP slot, propagated through a scoped client context to the existing RSVP preview placement. Public page supplies the generic form only when enabled and an RSVP page exists, otherwise null. Other renderer callers supply no slot and preserve their disabled preview. Existing page layouts/title/text/contact remain intact. This avoids duplicating renderer layouts or merging personalized and generic identity.

Generic payload contains only public ID plus first_name, nullable last_name, status and string answers per person. Names trim, first name is required and both have max length 100; empty last name becomes null. Attendance has only attending/not_attending. Questions use current page.rsvp config; legacy pages use existing attendance defaults and no custom questions. Required validation applies only to attending; declining clears answers. Server action re-reads public context, checks enabled/page/guest count and current questions, then calls submit_generic_rsvp. It strips answers outside current question IDs. Success JSON is validated as success:true and submitted_at timestamp. Capacity is never calculated in application code; the existing RPC remains authoritative.

UI supports adding/removing additional people, preserves one person, disables add at the per-submission maximum and locks submission while pending. Success replaces the form without an edit/resubmit CTA. No cookie/storage identity, recipient/token, Project Guest lookup, personalized identifiers, or direct table access exists. Errors use stable application codes and localized HR/EN messages; no raw RPC errors or request payloads are logged. New error codes are RSVP_CAPACITY_EXCEEDED and RSVP_GUEST_LIMIT_EXCEEDED; existing invalid/unavailable/answers/submission codes are reused.

Personalized flow, recipient management, builder schema, generic settings and database are unchanged. A narrow renderer test dependency was updated for the new default-empty slot. Validation/tests cover public settings, disabled/no-section, legacy, mixed people, limits/names, current questions, decline clearing, payload isolation, capacity mapping, success parsing, UI lock, and disabled preview/personalized regressions. Live database locking and real browser rendering require integration verification; mocked tests do not establish those properties.
